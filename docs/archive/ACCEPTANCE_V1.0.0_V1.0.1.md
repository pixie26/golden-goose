# V1.0.1 复核结果与上线验收

复核日期：2026-11-18。

## 结论

**V1.0.0 的结论"没有留下已复现、尚未修复的阻断问题"不成立。** 按 [NETLIFY.md](../NETLIFY.md) 连接 Supabase（`?sslmode=require`）时，所有接口都返回 503，网站连首次设置页都进不去。原因和修复见 [CHANGELOG.md](../../CHANGELOG.md)。V1.0.0 的真实数据库检查连接的是不带 TLS 的本机数据库，所以没有发现这个问题。

V1.0.1 已修复，并通过下表全部检查。在本轮能执行的检查范围内，没有发现剩余的上线阻断。这不等于保证不存在其他缺陷，也不能代替你在自己的 Netlify + Supabase 上完成下方"上线最后验收"。

## 本轮没有完成的项目

- **你的 Netlify + Supabase：** 本轮用本机 PostgreSQL 加私有 CA 模拟 Supabase 的证书信任情况，用代理模拟 pooler 丢弃启动参数，没有连接你的账号。
- **真实 iPhone / iPad Safari：** 只在 Chrome 中按手机尺寸测试过。
- **Yahoo 线上可用性，以及定时任务在已发布部署上的实际触发。**

## 已知问题（不影响上线）

- `/api/state` 每次返回完整流水，供"交易记录"页的"全部时间"使用。V1.0.2 起不再返回页面用不到的审计记录。按每天约 7 次操作的高估口径计算，返回内容每年约增加 0.5 MB（家长）和 0.6 MB（Olivia），约 10 年后才会接近 Netlify 6 MB 的响应上限，家庭使用不需要分页。
- 每次函数冷启动都会重新执行建表和权限语句。这些语句可以重复执行，但会短暂锁表；可以改为先检查再执行。

### 业务与接口回归

覆盖登录权限、会话失效、失败登录限制、账户切换、注资、购物预算及预留、单步审批与扣款、退款时限及一次机会、定存及提前赎回、借款额度及全部还清、任务验收、心愿转购买、碎股买卖、订单撤销、交易日历及半日市、收盘确认窗口、报价验证、前端草稿保护、后台轮询、中文提示、分页默认条件、一位小数显示与头像校验。

新增回归明确验证：

- 超过旧保留数量后，流水、审计和已处理请求标识仍保留；旧操作重放不会再次入账。
- 同一请求键不能更换金额或操作；旧开发版账本中已有的请求键仍被识别。
- 极小碎股拆单不会凭分钱四舍五入增加现金；不足一分的卖单不扣持仓。
- 未收盘日线、无效日期、非法数值输入不能成为成交依据。
- PIN 重置会解除旧登录锁定并撤销旧会话。
- 任务、利率及无持仓报价更新会触发页面同步；输入框聚焦和未提交草稿不被后台刷新覆盖。
- 超时或丢响应后可复用请求键；同一标签页刷新可恢复未确认动作，成功后的合法新操作不会被吞掉。
- 流式请求大小限制、JSON 对象校验和完整 Origin 校验有效。
- 数据库空闲连接失败、初始化失败、回滚失败及不确定 COMMIT 不触发自动重复记账。

### 真实数据库十项检查

1. 两个独立进程同时冷启动，创建同一张表和唯一账本行。
2. `anon` 和 `authenticated` 实际连接不能读写账本。
3. 临时授予 SELECT 后，默认拒绝的 RLS 仍返回零行。
4. 两进程并发完成 50 次入金，50 笔均保留、总额准确。
5. 同请求键并发入金，只提交一次。
6. 同请求键并发定存扣款，只开一笔定存、只扣一次。
7. 内存账本修改后主动抛错，现金、流水、审计及幂等信息全部回滚。
8. 超可用金额的业务失败，持久账本完全不变。
9. 应用进程重启后能读取完全相同的已提交账本。
10. 数据库真实停止 / 再启动后，账本 JSON 完全一致。

数据库账户是非超级用户、没有 BYPASSRLS 的表 owner；仅使用 127.0.0.1 临时数据库及合成资料。该测试验证 PostgreSQL 本身的 SQL、锁、权限和事务，不代替 Supabase pooler / TLS 云端连接验收。

### 函数打包检查

官方打包工具正确识别 `bank` 的 `/api/*` 路由，以及 `daily-settlement` 的 `30 9,22 * * *` 调度。两个产物及生产 pg 依赖均可载入，缺少环境变量时返回可控 503 并禁止缓存。

- **用户实际线上环境：** 没有提供或连接 Netlify / Supabase 账号，未验证实际网络、TLS、环境变量、域名、云端权限和发布流程。
