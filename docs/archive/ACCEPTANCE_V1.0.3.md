## 三项问题的修复验证

### RGG-001：补行情顺序不再改变成本

同一证券先规范假期目标，再按目标交易日、提交时间和稳定提交次序结算。较早订单缺少最终报价或未达到结算时刻时，同股晚单继续等待；其他证券独立处理。执行排序不改变页面订单列表次序。

合成价格复现：先以 100 O$ 买入 1 股，之后目标日卖出 1 股 @150，再隔日买入 1 股 @200。逐日返回、两天一起返回、报价行逆序、晚一天报价先到，最终都得到：

| 项目 | 修复后结果 |
|---|---:|
| 现金 | 150 O$ |
| 剩余股数 | 1 股 |
| 剩余成本 | 200 O$ |
| 已实现盈亏 | +50 O$ |
| 未实现盈亏（最新价格 200） | 0 O$ |

家长重算或顺延交易日，不能把订单移到同股已经完成的成交之前。若升级前已存在“早单待成交、晚单已成交”，系统保留原预留与记录，暂停该证券并提示核对历史成本；不会自动撤单或修改已成交账务。解除等待或撤单后清理本轮等待提示。

对应回归：`tests/settlement-order.test.mjs`。

### RGG-002：连接中断返回受控错误，原进程继续服务

每个 PostgreSQL 客户端只注册一次持久错误监听，坏连接销毁。初始化及业务事务均覆盖，没有金融 callback 自动重放。

真实 PostgreSQL 与 TCP 代理验证：

- **callback 等待期间、没有 SQL 查询时断线：** callback 只执行一次；改动全回滚，余额保持 200 分；同一进程重试后为 500 分。
- **COMMIT 已提交、确认回包丢失：** 等到 PostgreSQL 的 `CommandComplete: COMMIT` 后才吞掉回包并断线。API 返回 JSON 503、`BANK_STORE_UNAVAILABLE`、`Cache-Control: no-store`；同一进程随即成功处理 bootstrap；同请求键重试返回 `duplicate: true`，余额保持已提交的 800 分。

对应回归：`tests/database-recovery.test.mjs`、`tests/postgres-integration.test.mjs`。

### RGG-003：弱网恢复保留原股票选择

生产前端与真实业务核心共同验证：点击 NVDA 买入、注册成功、紧接着账户读取失败时，保留 NVDA 待选状态，不展示另一证券的买入表单。手动刷新、空闲恢复、轮询或重试选择后，都恢复 NVDA；用户提交表单后实际创建的订单仍是 NVDA。

用户明确改选其他股票后，旧请求的返回不能覆盖新选择。注册失败显示真实错误；退出、会话失效或账户切换清理待选状态。恢复过程不会自动下单。

对应回归：`tests/stock-selection-recovery.test.mjs`。

## 重跑方法

普通检查：

```bash
npm ci
npm run verify
```

真实数据库检查使用专用测试库，数据库名称必须包含 `test`；测试会重建该库中的 `bank_state`。在本地配置 `TEST_DATABASE_URL` 和可选的 `TEST_DATABASE_CA_CERT` 后执行：

```bash
node --test tests/postgres-integration.test.mjs
```

本轮连接使用 `sslmode=verify-full` 与匹配的 CA。连接信息不要写入仓库。可选 `TEST_DATABASE_POOLER_URL` 让锁等待检查经过测试 pooler；不要将测试连接指向生产数据库。

## 已有股票历史的升级边界

本版不会自动重算已经成交的历史成本。如果 V1.0.2 曾发生乱序成交，应先备份，再根据完整成交记录核对成本与盈亏；旧版历史若已截断，需要找回原始记录，不能用当前余额反推。详见 [OPERATIONS.md](../OPERATIONS.md)。没有股票交易历史的新账本无需这项处理。
